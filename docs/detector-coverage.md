# Detector label coverage

How many labelled examples the UI detector's training set has for each element class, item and item group, what
Roboflow's guidance says we need, and how to close the gap (mae, 2026-11-10). Design of the detector:
`detector-design.md`. Numbers are what `python -m sxs dataset` would export: confirmed boxes only, private screens
(guild, chat, profiles, rankings) left out.

**Source of the numbers below:** `docs/screens/labels.json` on branch `labels/check-drafts` at `aee0169` (PR #55,
mae's final labeler pass, 0 drafts) with the item catalogue at 109 entries. Refresh after every labeling pass:

    python3 scripts/label_coverage.py --write

## Summary

- **609 exportable boxes on 105 screens.** 354 of them (58%) are `item_icon`; the other 255 spread over 23 of the
  43 element classes. 85 more boxes sit on private guild and profile screens and never reach the export.
- **19 element classes have no box at all**: every card class, `btn_close_x`, `btn_tap_to_spin`, `btn_quick_heal`,
  `map_chest`, `map_zone_label`, `map_pct_line`, `monster`, `npc_alert`, `tracker_box`, `anchor_dialogue_box` and
  `anchor_popup_panel`.
- **Only one element class besides `item_icon` meets the minimum below** (`badge_red_bang`, 64 boxes on 25 screens). `item_icon` as a
  single class is well covered (354 boxes, 87 screens).
- **Items one class each (`--items each`) cannot work yet.** The best item has 48 boxes on 19 screens; 36 of 109
  items have no box. **Per material group (`--items group`)**, the plan for the first training, two groups meet the
  minimum (`prayer_ticket`, `currency_token`) and `ore` is one box short.
- **Most classes are missing from the valid and test splits.** The export splits by screen hash 80/10/10, so a
  class on 3 screens usually lands only in train and the model is never scored on it.
- **The bank already holds most of what we need.** 223 public reference frames have no box, and a visual pass over
  them (below) finds most of the missing classes on screens we already have. New screenshots are needed mainly for
  cards, area maps and world-map variety.

## What Roboflow says, and the target we use

Roboflow gives no hard per-class number. What it does say:

- "It is recommended [to start] with approximately 50-100 images for the first model version", and for "a narrow
  task with one visually distinct object, 50-100 diverse images may be enough for a useful prototype"; a production
  system "may later require hundreds or thousands"
  ([Roboflow, YOLO training](https://roboflow.com/blog/yolo-training)).
- "Make sure each class has enough examples. If some objects are rare, try to include more of them", and "every
  train, validation, and test split should include all classes"
  ([Roboflow, how much training data](https://roboflow.com/blog/how-much-training-data)).
- "When a rare class is important, collect more examples rather than relying only on oversampling or augmentation"
  (YOLO training post above). Its imbalance guide lists more data first, then augmentation, oversampling and
  re-weighting, applied to the training split only
  ([Roboflow, handling unbalanced classes](https://roboflow.com/blog/handling-unbalanced-classes)).
- The project's Health Check page shows class counts per split but sets no threshold
  ([Roboflow docs, dataset health check](https://docs.roboflow.com/datasets/dataset-health-check)).
- For scale, Ultralytics (the YOLO authors) recommend at least 1,500 images and 10,000 instances per class for
  best results ([Ultralytics, tips for best training results](https://docs.ultralytics.com/yolov5/tutorials/tips_for_best_training_results)).
  That is a production bar for natural photos; our elements are fixed game sprites at a fixed resolution, so far
  fewer examples go further, and we don't plan for it.

**Target for the first training run (per class):**

| Level | Boxes | Images (distinct screens) | Why |
|---|---|---|---|
| Minimum | 50 | 20 | Roboflow's 50-100 first-version figure, applied per class; 20 screens gives about 2 each in valid and test at our 80/10/10 split, so every class is scored |
| Good | 100 | 50 | Top of Roboflow's first-version range, with real variety in background and position |

Classes under the minimum should still be trained if they have a few examples, but their scores are not to be
trusted until they reach it. Augmentation (light only, mae's rule) multiplies training images but does not count
toward these numbers, since it adds no new screens. After the first training, the per-class scores decide where
the next labels go (Roboflow's active-learning advice).

## Things the numbers turned up

- **`unknown_1` is a stale item id.** 2 boxes on `items/` screens still say `item: unknown_1`, which the catalogue
  has since named `growth_trial_points`. The export leaves them as plain `item_icon`. Fix in the labeler (rename the
  item on those boxes) or in the next merge.
- **`btn_quick_heal` and `anchor_hud_portrait` describe the same box** (the top-left portrait, R-078). Two classes
  on one identical region teach the model to guess between them. Either drop one, or make `btn_quick_heal` mean the
  separate "Quick Heal" button on the wounded dialog and player profile. Vision thread's call.
- **Price buttons get their own class, `btn_price`** (mae, 2026-11-10). The yellow USD and Dawnium buttons in the
  Mall, Vendor Booth and purchase prompts look like `btn_primary`; left unlabelled the model would learn them as
  background and fire on them anyway. With their own class the bot can refuse them by class as well as by the text
  check (hybrid design). The class is to be appended to `resource/detect/classes.json` by the vision thread (never
  reorder); then box every price button on the shop screens as `btn_price`, never as `btn_primary`.
- **Splits.** Of the 23 element classes with boxes (not counting `item_icon`), 12 have no valid image and 17 have no test image. Roboflow can
  rebalance splits when a version is generated, but our upload sets them by folder. For the first run, either
  rebalance in Roboflow or have the export guarantee each class at least one screen in valid and test (vision
  thread owns the export).
